# ADR 001: статическое приложение на React и Vite

- Статус: принято как рабочее решение
- Дата: 30 июля 2026 года
- Требует подтверждения заказчика: способ размещения внутри «Энергии+»

## Решение

Разрабатывать игру как одностраничное клиентское приложение на следующем стеке:

- `React`;
- `TypeScript` в строгом режиме;
- `Vite` для локальной разработки и статической сборки;
- `Bun` как менеджер пакетов и исполнитель JS-команд;
- CSS Modules и CSS custom properties для компонентов и дизайн-токенов;
- нативный `useReducer` + Context для состояния прохождения;
- `Motion for React` только для переходов, которые сложно выразить CSS;
- `Vitest` + React Testing Library для логики и компонентов;
- `Playwright` для полного прохождения на desktop и mobile viewport;
- `Biome` для форматирования и статических проверок;
- `go-task` как единая точка входа в команды проекта.

Приложение не требует Node.js-сервера после сборки. Команда `vite build`
создаёт каталог `dist/` с HTML, CSS, JavaScript и локальными ресурсами.

## Почему этот вариант AI-first

`AI-first` здесь означает не наличие AI внутри продукта, а предсказуемую
архитектуру, которую coding agents могут безопасно читать и изменять:

1. React, TypeScript и Vite имеют широко известные API и большой объём актуальной
   документации и примеров.
2. Строгие типы превращают сценарные ошибки в ошибки сборки.
3. Игровой контент отделяется от компонентов и хранится в типизированных
   декларативных объектах.
4. Один reducer содержит все допустимые переходы игры и начисление баллов.
5. В проекте нет серверных компонентов, скрытой генерации маршрутов, ORM и
   другого контекста, который агенту пришлось бы восстанавливать.
6. Сценарий, UI, аналитика и хранение прогресса получают отдельные контракты и
   могут изменяться независимо.

## Предлагаемая структура

```text
src/
  app/                 # композиция приложения и providers
  content/
    recipients.ts      # получатели и грамматические формы
    parcels.ts         # грузы и ограничения
    scenes/            # пять декларативных сценариев
  game/
    model.ts           # типы состояния и событий
    reducer.ts         # переходы, баллы, завершение
    selectors.ts       # вычисляемый профиль и прогресс
  components/          # общие UI-компоненты
  screens/             # онбординг, сцена, результат, эпилог
  integrations/
    analytics.ts       # адаптер аналитики / postMessage
    persistence.ts     # localStorage или no-op
  styles/
    tokens.css         # палитра, типографика, сетка, motion
  assets/              # локальные SVG, изображения, шрифты
```

Сцена описывает входные данные, варианты, результат, изменение показателей и
следующий переход. Компоненты не должны содержать продуктовые тексты и баллы.

## Маршрутизация и состояние

Полноценный роутер на первом этапе не нужен: игра представляет один линейный
сеанс с ветвящимися результатами. Текущий экран и история решений находятся в
reducer.

Если понадобится ссылка на конкретный результат, используется URL hash. Это не
требует server-side rewrite и работает на любом статическом хостинге.

Прогресс можно сохранять в `localStorage`, но только после подтверждения
заказчика. Приложение должно работать и с отключённым сохранением.

## Стили и графика

UI-библиотека и готовая дизайн-система не используются: они будут конфликтовать
с фирменной графикой «Энергии+». CSS Modules изолируют компоненты, а общие токены
задаются CSS-переменными.

Интерфейс остаётся DOM-based, а не Canvas-based. Это упрощает адаптивность,
текст, доступность, аналитику и автоматические тесты. SVG используется для карты,
транспорта, масок и интерфейсных иллюстраций.

Простые состояния и переходы реализуются CSS. `Motion for React` подключается
для появления сцен, смены результатов и движения по маршруту. GSAP и игровой
движок не нужны без доказанной необходимости.

## Статическая сборка

Vite официально создаёт bundle для обычного статического хостинга. Для
переносимого архива используется относительная база:

```ts
export default defineConfig({
  base: './',
});
```

Так пути к JS, CSS, изображениям и шрифтам остаются относительными, даже если
каталог игры размещён не в корне домена. Динамическое составление путей вручную
не допускается; ресурсы импортируются через Vite или используют
`import.meta.env.BASE_URL`.

Все зависимости, шрифты и ассеты кладутся в сборку. Внешние CDN не требуются.

## Размещение в Tilda

Tilda поддерживает HTML, CSS и JavaScript в блоке `T123`, но произвольный архив
приложения она сама не разворачивает. Экспорт Tilda работает в обратную сторону:
выгружает созданный в Tilda сайт на собственный сервер и доступен только на
Business Plan.

### Предпочтительный вариант

1. `dist/` публикуется на статическом хостинге или в каталоге инфраструктуры
   заказчика, например `https://game.example.ru/logistics/`.
2. В Tilda добавляется `T123` или HTML-элемент Zero Block с полноэкранным
   `iframe`.
3. Игра использует `100dvh`, не имеет внешних отступов и сама управляет своей
   адаптивностью.

```html
<iframe
  src="https://game.example.ru/logistics/"
  title="Игра-квест «Доставляем радость»"
  loading="eager"
  allow="fullscreen"
  style="display:block;width:100%;height:100dvh;border:0"
></iframe>
```

Преимущества:

- стили и JavaScript Tilda не конфликтуют с приложением;
- один и тот же `dist/` работает в Tilda и отдельно;
- обновление игры не требует вставлять minified-код в редактор;
- проще тестировать staging-сборку и откатывать релиз.

### Допустимая альтернатива

Если сайт экспортируется из Tilda и заказчик контролирует его сервер, `dist/`
можно положить в каталог того же домена и встроить через same-origin `iframe`.

### Нежелательный вариант

Монтировать React напрямую в `T123` и загружать JS/CSS с внешнего адреса можно,
но это создаёт риск конфликтов CSS, глобальных скриптов и жизненного цикла
страницы. Этот режим допустим только как запасной после теста на реальной
странице.

Single-file HTML и вставка всего bundle в поле T123 не являются основным
вариантом: такой артефакт неудобно проверять, обновлять и кэшировать.

Tilda выполняет пользовательский код только после публикации страницы, поэтому
нужна отдельная тестовая опубликованная страница.

## Интеграции без backend

- Аналитика отправляется через адаптер. Для cross-origin iframe предпочтителен
  `window.parent.postMessage`, а родительская страница преобразует события в
  события Яндекс Метрики или другой системы.
- Игра не собирает персональные данные без отдельного согласованного сценария.
- Cookie-based аналитика должна учитывать механизм согласия Tilda.
- Финальные CTA являются обычными ссылками, полученными из конфигурации сборки.
- Отправка результатов, лидерборд, конкурсная регистрация и синхронизация между
  устройствами невозможны без внешнего сервиса или backend и не входят в этот
  стек.

## Почему не другие варианты

| Вариант | Решение |
| --- | --- |
| Next.js static export | Работает, но добавляет маршрутизацию и server-oriented абстракции без пользы для одной интерактивной игры. |
| Astro + React | Почти всё приложение было бы одним интерактивным island, поэтому слой Astro не даёт преимущества. |
| SvelteKit static | Технически подходит, но добавляет adapter-specific сборку и имеет меньше React-совместимых примеров и библиотек для AI-assisted разработки. |
| Preact + Vite | Уменьшает runtime, но имеет отличия в событиях и совместимости. Переход оправдан только после измеренного performance-проблемы. |
| Vanilla TypeScript | Не требует UI-runtime, но усложняет управление интерактивными экранами, состоянием и повторным использованием компонентов. |
| Phaser | Canvas-движок избыточен для квиза и карты, ухудшает доступность и работу с адаптивным текстом. |

## Проверки перед фиксацией интеграции

Нужно получить от команды площадки:

1. реальную опубликованную тестовую страницу Tilda;
2. выбранный вариант хостинга `dist/`;
3. допустимый домен или подкаталог игры;
4. CSP и правила iframe;
5. браузерную матрицу;
6. контракт аналитики и cookie consent;
7. лимиты веса первого экрана и полного архива.
